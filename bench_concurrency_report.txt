== 三、结论 ==
1. 判题吞吐在 1.5–1.6 题/秒封顶：并发从 1 涨到 20，QPS 只从 0.41 到 1.6，
   而 P99 从 3.3s 涨到 19.7s——典型的同步阻塞退化，请求在排队而不是在并行。
2. 瓶颈不是 Web 层，是每次提交都要起 javac + java 两个子进程。
   与 bench_report.txt 的"678ms/用例、与算法复杂度无关"互相印证。
3. 接口层即使走编译失败短路径，50 并发 QPS 也只有 8.36，
   平均响应 5.5s——说明连短路径也被 CPU（编译进程）卡住，不是纯 IO 型接口。
4. 当前架构的真实定位：单机、串行判题、适合几十人规模的课程/小团队使用；
   要支撑更高并发，必须把"提交"和"判题"解耦成异步队列。

== 四、复现方式 ==
java -jar target/oj-0.0.1-SNAPSHOT.jar --server.port=8080 --oj.rate-limit.submit.limit=1000000
python bench_concurrency.py --levels 1,5,10,20 --mode real
python bench_concurrency.py --levels 10,50 --mode fast
